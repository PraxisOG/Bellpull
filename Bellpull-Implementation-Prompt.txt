YOUR MISSION

You are the implementation agent continuing an existing native Android app.
The app's new name is Bellpull. Hermes is the self-hosted agent backend.
Evolve the working application into a dependable Fold-oriented workspace for
conversations, project knowledge, files, voice, and remote coding sessions.
Preserve existing functionality and visual quality. Keep the custom bridge or
Hermes plugin compact. Reuse existing backend features before adding new ones.

This is an execution brief, not a request to build a replacement app, produce
another conceptual roadmap, or implement every item from a prior brainstorm.
Only the selected scope in this document is the backlog.

EXECUTION DEFAULT

- If the accompanying user request specifies a phase, implement that phase and
  its necessary prerequisites. Otherwise start with Phase 0 and progress through
  the implementation-ready phases in order, in small verified increments.
- After a normal phase succeeds, record its evidence and continue. Do not require
  a new confirmation merely because a phase boundary was reached.
- Resolve routine engineering choices yourself. Ask only when missing access,
  conflicting requirements, consequential migration choices, or an unresolved
  product decision actually blocks the next useful step.
- Research-dependent work has a decision checkpoint, not permission to invent
  support. Complete a bounded feasibility investigation; implement when justified,
  or record the concrete blocker and continue independent work.
- Follow repository instructions and the execution environment's permissions.
  This brief does not authorize production deployment, publishing releases,
  sending messages to other people, or deleting unrelated data.
- Save progress in the repository's existing planning convention. If none exists,
  use a concise BELLPULL_PROGRESS.md with requirements, decisions, validation,
  blockers, and the next action. Reuse it after compaction or agent handoff.

The user reports that Moe already runs Qwen 3.8 Flash Next at approximately
50 tokens/second. Hermes will run on Moe for now. Treat the model name and speed
as user-reported; discover the actual configured model ID and endpoint rather
than guessing them. Do not turn this task into rebuilding the inference server.
Moe has four AMD Radeon Pro V620 GPUs. The intended primary phone is a Pixel
10 Pro Fold. Confirm the actual Android version, build configuration, and test
device when implementation begins.

No repository, installed Hermes commit, app transport, database schema, Android
UI toolkit, or live endpoint was inspected while writing this brief. Public
documentation consulted during planning is a discovery lead, not proof that the
installed version or custom bridge exposes a feature. URLs appear at the end.
Avoid hardcoding imagined APIs, model capabilities, credentials, or file paths.

Verify this baseline against code and a running build. Record differences without

NON-NEGOTIABLE IMPLEMENTATION PRINCIPLES

1. Extend the current app, transport, persistence layer, and component library.
   Keep changes scoped and reviewable. Avoid framework migrations or a Hermes fork
   unless a demonstrated requirement cannot be met through a supported extension.
2. Keep local processing the default where practical. Preserve the user's existing
   Hermes web-search configuration. Do not quietly add cloud STT, TTS, embeddings,
   telemetry, analytics, or inference fallbacks.
3. The phone owns presentation, navigation, transient selection, draft editing,
   read position, and device actions. Hermes owns its agent sessions, tool execution,
   configured memory, and backend job lifecycle. Shared metadata should have one
   explicit authority; cache it on the phone rather than inventing competing truth.
4. Use stable identities for conversations, messages, runs, tool calls, attachments,
   saved items, and projects. Resolve whether upstream IDs survive edits/rewinds;
   provide safe mappings where they do not.
5. Reuse supported Hermes APIs. If an extension is necessary, add the smallest
   versioned, authenticated operation to the current bridge and document why.
   Never have Android directly edit a live Hermes SQLite database.
6. Reading cached content, switching tabs, marking a chat read, rendering cards,
   listing files, and other deterministic UI operations must not invoke an LLM.
7. Distinguish missing/unsupported, loading, running, completed, failed, cancelled,
   and stale states. Do not display a control that silently does nothing.
8. Preserve privacy boundaries and existing tool approvals. Displaying a tool's
   completed result must never execute the tool again. Retrieved chat/file content
   is data, not a source of new instructions or permissions.
9. Respect fold transitions, system font scaling, touch targets, keyboard insets,
   accessibility labels, and reduced-motion settings. Small icons may have larger
   invisible hit areas. Keep implementation jargon out of ordinary product flows.
10. Verify behavior proportional to risk. Prioritize real reconnect, file, voice,
    and state-transition tests over large suites that merely mirror implementation.
    Never claim device-only behavior was tested when only compilation or mocks ran.

Reserve a Today entry marked "Coming soon" until its later-phase implementation.

the selected Android widget framework.

ROADMAP AND DEPENDENCIES

Phase 0: Inspect the real system and establish capability/data contracts.
Phase 1: Bellpull branding, navigation, and everyday chat interaction.
Phase 2: Reliable runs, delivery state, unread state, notifications, approvals,
         server profiles and a usable disconnected experience.
Phase 3: Model controls, uploads, artifact previews, sharing, GPU telemetry.
Phase 4: Projects, saved answers, contextual search, memory, history imports.
Phase 5: Complete natural voice conversation.
Phase 6: Multiple remote coding sessions and optional response comparison.
Phase 7: Today/device assistant features and on-phone inference/synchronization.

Phases are usable releases, not one enormous change each. Use the slices below.
Phase 1 may render the dashboard structure, but Phase 2 owns proving live behavior.
Phase 4 uses Phase 3's attachment identities. Phase 5 depends on model routing and
reliable session control. Phase 6 reuses Phase 2's run/approval architecture.
Phase 7 can ship reminders and widgets independently of on-device inference.
A bounded CPU-inference feasibility experiment may happen earlier if the actual
phone is available; it must not stall the core online app.

PHASE 0 — INSPECT, MAP, AND PROVE THE EXISTING CONNECTION
============================================================

Goal: determine the smallest real integration path before choosing API shapes.

Tasks

0.1 Read repository instructions, inspect git state, build scripts, app structure,
    persistence, current plugin, and networking. Preserve uncommitted user work.
    Identify the correct build/install workflow and establish one baseline build.
0.2 Record the Android toolkit and dependency versions, min/target SDK, app ID,
    current navigation/state ownership, and existing test/preview facilities.
0.3 Discover Hermes version/commit, enabled features, transport family, configured
    model provider, and the bridge's routes. Protect credentials in all reports.
0.4 Trace one message from composer to backend to stream to saved history. Trace
    stop, branching, tool cards, history/search, and reopening a conversation.
0.5 Map capabilities into: supported/exposed; supported upstream but not exposed;
    missing from installed version; unknown; custom extension required.
0.6 Specifically check:
    - Run creation independent of a phone-held connection.
    - Stable request IDs/idempotency, event replay, status lookup, saved history.
    - What happens after stream loss, app backgrounding, and a backend restart.
    - Steering versus interruption versus queued prompts, including while busy.
    - User-message editing/branching semantics and durable message identity.
    - Approval request/response/cancellation and rehydration after reconnect.
    - Model selection, genuine thinking disable, supported reasoning levels.
    - History search tool, memory read/write, desktop/project APIs if available.
    - Image inputs, generic upload/download, attachment retention and extraction.
    - Local STT/TTS providers and whether the app can reuse their transports.
    - Coding CLI sessions and the supported programmatic control of each runner.
0.7 Inspect actual amd-smi availability/output on Moe when access is provided.
    Treat missing sensors as unavailable. Do not install drivers or reconfigure
    the working GPU stack merely to fulfill a cosmetic panel.
0.8 Write a compact ownership/contracts note. Extend existing project docs if
    possible rather than creating many redundant documents.

Acceptance

- Baseline build status is recorded; baseline regressions are distinguished from
  pre-existing issues.
- Each integration above has evidence or an explicit unknown, not a guessed API.
- A selected transport can represent sessions, messages, runs, tools, and errors.
- The smallest backend changes are identified with alternatives considered.
- If remote access is absent, client-only work continues against existing contracts
  or narrow fixtures, and runtime integration remains visibly unverified.

Do not stop after this investigation when implementation is otherwise possible.

PHASE 1 — BRANDING, NAVIGATION, AND CHAT INTERACTION
============================================================

Goal: make the existing application easier to navigate and work in every day.

1A. Branding and application structure

- Change user-facing app name, launcher label, about/help strings, and relevant
  app-specific documentation to Bellpull. Keep genuine Hermes backend names.
- Use the supplied approved icon with adaptive/circular safe areas where possible.
  If absent, leave icon integration pending while completing the name change.
- Preserve applicationId, signing identity, installed data, DB names, deep links,
  and transport identifiers unless there is a justified, deliberate migration.
- Implement NAV01–NAV07's architecture. Keep future destinations honest.
- Introduce a real Settings surface, initially for appearance/interaction defaults
  and "Collapse thinking by default" (enabled by default).
- Retain fold-aware panes and the existing + / ⋮ visual anchor.

1B. Composer and conversation behavior

- Keep a separate composer draft per conversation. Switching chats or modes must
  restore that chat's draft. Preserve cursor/selection where existing state permits.
- The user requires per-chat drafts during normal app navigation. Surviving app
  restarts is optional, not an acceptance gate for this slice. Fold/configuration
  transitions must not accidentally erase drafts.
- Add Edit on user prompts. Prefer implementing edit-and-resend via the current
  branch mechanism while preserving the original conversation. Explain the branch
  result clearly and keep the edited text recoverable if submission fails.
- If the installed interface cannot support editing a user turn without rewriting
  history unsafely, document the limitation and use an explicit fork-and-edit flow.
- Add "Follow up" to the selection menu for selectable message text. Carry the
  selected quote and source message reference into the composer, then focus input.
  Do not auto-send. Provide an equivalent explicit action if the renderer cannot
  expose it in the native selection toolbar. Record the remaining toolbar gap.
- Extend the existing jump-to-bottom control into the regular conversation view.
  Show it when the user is away from the live end; do not force-scroll while the
  user reads older content. One tap returns to the latest content.
- Render model-emitted thinking as a separately expandable block, collapsed by
  default. Global preference controls the initial state; a user can expand a
  particular block. Do not fabricate reasoning for models that do not emit it.

1C. Search surface and tool-call presentation

- Reuse the prompt-history menu format for expanded conversation search.
  Preserve current conversation/app-search functionality during extraction into
  reusable components. Agent history search is implemented in Phase 4.
- Group consecutive tool calls within an assistant turn into a single container.
  A second call grows it into two rows with a divider; preserve independent
  input/result expansion and copy actions for every row.
- Animate an arriving row as emerging from beneath the previous row and settling
  below it. Respect reduced motion and use stable keys so history replay does not
  repeat entry animations or reorder content.
- Preserve assistant commentary in chronological position. Do not merge tool
  groups across intervening messages, distinct turns, or distinct sessions.
- Keep a large group compact with an expansion control. Avoid unbounded height
  and scroll jumps. Tool state updates should modify the correct row in place.

Acceptance

- Existing sessions/data survive the Bellpull update and reopen correctly.
- Cover and unfolded views remain usable in light/dark themes and with keyboard.
- Clicking Conversations or its magnifier opens the same expanded search surface.
- Switching A -> B -> A preserves A's draft; folding and switching modes do too.
- Quoted follow-up includes the intended selection, is editable, and is not sent.
- Editing preserves the original path and starts the revised branch correctly.
- Jump-to-bottom works during streaming without pulling a reader down prematurely.
- Two consecutive tools show one divided group, retain their individual controls,
  and animate once; reload does not duplicate them.
- Thinking begins collapsed and respects the global preference and local expansion.

PHASE 2 — RELIABLE RUNS, UNREAD STATE, AND NOTIFICATIONS
============================================================

Goal: the phone can disconnect without losing work, duplicating it, or concealing
what needs attention. This phase covers the user's R1–R3 priorities.

2A. Request delivery and run recovery

- Separate request submission, transport subscription, and server execution.
  The ongoing work must not rely on keeping one Android screen or socket alive.
- Correlate a submitted request with a stable client-generated identity and the
  resulting server run. Reuse backend idempotency if available; do not invent
  an exactly-once guarantee for arbitrary external tool side effects.
- An ambiguous network failure must trigger reconciliation/status lookup using
  the same identity before resubmission. Never blindly create a fresh run.
- Keep unsent/pending/failed text recoverable with clear retry/cancel choices.
  Clear the submitted draft only after acceptance is known. A delayed acceptance
  must not wipe newer text the user has already typed into that chat.
- Restore missed events when supported; otherwise reconstruct from current run
  status and durable history. Event buffers may be transient; do not treat them
  as the only transcript or artifact store.
- Recover partial active output as far as the real backend supports it. Report
  any unrecoverable partial stream honestly instead of inventing content.
- Show stale/offline states. Reconnect must not replay tools or create duplicate
  tool cards, assistant messages, or notifications.
- Distinguish phone disconnect from server/process crash. Continuing through a
  backend crash is not promised unless actually supported and verified.

2B. Read state and dashboard

- Maintain a per-chat read position using stable message/event identity.
- Mark content read when it is actually viewed; merely reopening a chat while
  scrolled far above the new reply must not consume every unseen message.
- Keep Running, Unread, Failed, and Needs attention conceptually independent.
  Populate the top-of-drawer dashboard with real state and actionable entries.
- Implement the bright top-right unread dot specified in NAV03. Clear it based
  on the read position, not simply on selecting a tile or receiving an event.
- Returning from a notification opens the correct session/result without losing
  another chat's draft or silently dismissing its pending request.

2C. Notification delivery

- Notify for meaningful unread assistant messages and requests needing attention.
  Do not notify per token or per routine tool-status update.
- Suppress redundant notifications when the relevant new content is actively
  visible. Coalesce updates sensibly, with channels for replies and attention.
- Choose a delivery mechanism compatible with the phone's actual setup and the
  local-first preference. Inspect any existing ntfy/UnifiedPush/FCM or other
  infrastructure before adding a dependency. No hidden reliance on Google push.
- Verify delivery when backgrounded and screen-locked. Document force-stop,
  permission, OS, and connectivity limitations without claiming impossible
  guarantees. Catch up on state after reconnect even when a push was missed.

2D. Basic approvals

- Discover genuine backend approval requests; the user has not implemented these.
- Show the operation, relevant arguments, target session, and available decision.
- Link decisions to the specific pending request. Handle expiry, cancellation,
  decisions from another client, and reconnection. Never approve a different
  operation because a list position or UI object was reused.
- Reuse existing policy and operation handlers. Do not add blanket confirmation
  for every harmless action or remove configured approvals for convenience.

2E. Server profiles and disconnected exploration (user addition, 2026-10-09)

- Open directly into Bellpull without a mandatory login screen. Settings, appearance
  and clearly labelled local examples work without a server. Never imply that a
  disconnected demo runs an LLM or sends requests to the user's agents.
- Put server URL/API-key setup in Settings > Server profiles. Save named profiles
  so desktop testing and compute-server use can be switched without retyping keys.
- Keep credentials encrypted. Isolate cached sessions, drafts, read state, pending
  runs and notification identity by profile, including identical session IDs.
- Sign out to the disconnected workspace while retaining saved profiles for reuse.
  Offer explicit removal of one profile or all saved credentials and local account
  data. Explain that removal does not revoke a key on the server.
- Switching profiles closes old subscriptions and speech, clears visible old-server
  state, and prevents delayed responses/notification taps from affecting the new
  profile. Server work may continue; recover it when that profile is selected again.
- Migrate the existing saved connection and local state without losing user data.
  Never save API keys in UI saved-state bundles, logs, screenshots, or packages.
- Lead the GitHub README with a tested precompiled APK and install instructions.
  Once this slice ships, explain optional Settings-based connection and no-login
  exploration. Do not document unshipped behavior for an older APK.

Acceptance

- Fresh install opens a useful disconnected app; Settings and local examples work.
- Switching server A -> B -> A preserves each profile's own drafts and history.
- Sign-out persists after restart; removing a profile or all credentials actually
  deletes that local account data without modifying the remote agent.
- A late response, pending send, or notification from A never acts on B.
- Start a run, lock/close the app, and reopen: work remains tracked and history
  reconciles. A disconnect does not turn one submission into two runs.
- Lose the connection immediately around submission acknowledgement: reconcile
  the original request identity before any retry.
- An unsent message remains recoverable, including when changing chats.
- Completed unread work appears in the dashboard and the correct tile has a dot.
- Reading the new content clears the dot; reading older content alone does not.
- Notifications deep-link correctly and do not flood during streaming/replay.
- A real approval can be accepted/rejected once; stale approval UI cannot execute.
- Evidence states exactly which device/network/background cases were tested.

PHASE 3 — MODELS, FILES, PREVIEWS, SHARING, AND GPU METRICS
============================================================

Goal: make model choices and useful inputs/outputs accessible from the phone.
PDF and image previews are a high-priority outcome, not optional visual polish.

3A. Model and reasoning selection

- Put the model picker behind the existing model control in session/context info.
- Discover usable model routes and whether loading/switching is already handled
  by the server. Do not imply every downloaded model is instantly available.
- Add actual thinking on/off and supported reasoning-strength controls. Hiding
  a reasoning block is presentation only; disabling reasoning changes inference.
- Only expose settings the selected model/runtime can honor. Where no disable
  exists, show the limitation rather than relabeling minimum effort as "Off".
- Persist choices at the intended session scope; do not silently change defaults
  for other chats, cron jobs, or coding runners. Define defaults in Settings.
- Keep the effective selection visible, including a backend-rejected change.
- Generation parameters and system-prompt editing are low priority. If added,
  place them in an advanced context area, validate supported parameters, and keep
  reset-to-default behavior. Do not let them delay uploads, previews, or voice.

3B. Unified attachment transport

- Add file/image selection from the phone, plus camera capture where practical.
- Use Android's granted URI access correctly, including content-provider streams
  and the lifetime of permissions. Do not assume every URI is a filesystem path.
- Show upload progress, cancellation, failure, and retry. Preserve the draft and
  selected files when upload fails. Validate reasonable type/size limits.
- Reuse the real bridge's upload/download handling. If absent, add minimal
  authenticated artifact operations with stable IDs and metadata.
- Attachments need MIME type, display name, byte size, source/session associations,
  and upload/availability state. Preserve source bytes; derived previews/extracted
  text are secondary representations, not replacements for the original.
- Deliver images in the selected model/backend's supported format. Image upload
  does not prove the chosen model has vision; disclose unsupported routes and let
  the user select a capable configured route rather than silently using a cloud API.
- For non-image documents, inspect supported extraction tools before selecting
  a new pipeline. Avoid stuffing unlimited document text into every prompt.
- Backend filesystem paths must become authenticated phone-openable references.
  Avoid path traversal, raw credential exposure, or public artifact URLs by default.

3C. Previews, browsing, and sharing

- Render PDFs in-app with page navigation and zoom. Render images with pan/zoom.
  Keep a clear return to the originating chat and preserve scroll position.
- On the unfolded phone, allow preview content alongside discussion where the
  existing pane system supports it. On the cover screen, use a focused preview.
- Provide open/download/share fallback for unsupported formats; do not display
  success when only a local server path or broken link was returned.
- Build an attachment browser under Tools. Sort by at least date, filename, type,
  and size; filter by conversation and later project. Show source links.
- Make both uploaded and agent-generated artifacts discoverable through the same
  records where appropriate. Handle missing/unavailable files honestly.
- Implement Android share-in for text, links, images, and files into a chosen or
  new conversation draft. Do not auto-submit shared content.
- Replace sharing's current placeholder with share-out for answers and artifacts
  using appropriate content grants. Keep access temporary to the shared item.
- Limit HTML preview capabilities if HTML is supported; untrusted artifacts must
  not receive bridge credentials or arbitrary local/device execution privileges.

3D. GPU temperature panel

- Read actual amd-smi output or its supported library interface on Moe through a
  narrow authenticated endpoint. Cache readings server-side as appropriate.
- Show four stable GPU rows, each with a green-left to red-right temperature bar,
  a current marker/value, and an explicit sensor label (edge/hotspot/memory).
- Use meaningful fixed scales/thresholds for the selected sensor, documented from
  actual device support. Do not auto-normalize each bar so a cool card looks hot.
- Missing sensor data is unavailable, not zero degrees. Show sample time/staleness.
- Refresh modestly while visible; avoid continuous background polling and avoid
  launching a model/tool turn each time a temperature is refreshed.
- Do not add overclocking, power changes, driver changes, or fan control to this
  read-only statistics requirement.

Acceptance

- Model/reasoning selections reach the actual backend and persist at the right
  scope; unsupported options cannot masquerade as successful settings.
- Upload an image and a PDF from a real Android content provider. Retry failure
  without losing the draft or associating a file with the wrong chat.
- View both files and a generated artifact inside the app, including after leaving
  and reopening the conversation. Confirm protected download behavior.
- Share text/file into a draft and share an artifact out to a chosen app.
- Sort attachments and follow a result back to its source conversation.
- Four GPU rows identify the correct cards, handle unavailable readings, and stop
  unnecessary polling when the panel is hidden.

PHASE 4 — PROJECTS, SAVED KNOWLEDGE, SEARCH, MEMORY, IMPORTS
============================================================

Goal: make important information reusable across conversations without turning
every chat into an enormous concatenation of all previous chats and files.

4A. Saved answers and lightweight projects

- Add a star/bookmark action to assistant answers. A saved item should retain the
  source conversation/message, saved text or excerpt, save time, and optional note.
- Use this same feature for "Add to project". Avoid separate bookmark and project-
  clipping systems that duplicate content and lose the connection to its source.
- Support starring an answer without a project, and adding an existing saved item
  to a project later. Unstarring must not unexpectedly delete the original answer.
- Provide a Projects destination with collections of conversations, saved answers,
  user-written notes, and attachments. Let the user put important information there.
- Investigate native Hermes project support first. Distinguish repository/workspace
  projects from this broader knowledge-collection need. Reuse native IDs/interfaces
  where suitable, or store small collection metadata in the existing bridge.
- A project is not automatically a new Hermes profile, agent, memory system, or
  database. Do not create a parallel agent architecture to implement folders.
- Define a canonical store for project/saved-item metadata and a phone cache.
  Server-side context access must not depend on a particular Android screen being
  open. Version mutable records so later synchronization has a workable foundation.
- Proposed interaction default: "Save to project" stores/retrieves material;
  "Always include" explicitly pins selected short context. Other material is
  available for retrieval. Keep that distinction visible to the user.
- Let users inspect selected context and remove a reference before sending.
  Avoid silent truncation of pinned constraints; report context-budget conflicts.
- Preserve source links and saved excerpts if the original source later moves,
  branches, changes, or is deleted. Show a missing-source state where appropriate.

4B. Cross-chat context and filtered search

- Let the user bring another chat, selected messages, or a clearly labeled summary
  into the current conversation as referenced context. Preserve the original chat.
- Extend global search to message contents, not merely conversation titles.
- Include useful snippets and jump-to-match behavior. Preserve in-chat search and
  the existing prompt-history jump behavior.
- Add filter controls for supported metadata such as date, conversation/project,
  and attachment presence/type. Do not offer filters backed by invented metadata.
- Put "Semantic search" inside filters and keep it OFF BY DEFAULT. Keyword/full-
  text search must remain functional without an embedding service.
- When semantic mode is selected, use a local embedding/retrieval path compatible
  with the actual deployment. Prefer combining semantic and exact matches rather
  than losing literal filenames, names, and code symbols. Explain missing index
  availability without silently switching the query to an external provider.
- Semantic indexing should be incremental and versioned by model/index format.
  Do not re-embed the entire archive every time the user opens Search.
- Agent-accessible history search is a MUST. Verify Hermes's built-in session_search
  tool is enabled and sees the relevant Bellpull conversations. Expose the minimum
  bridge capability only if the actual store/transport requires it.
- Searches and follow-up reads should return actual source messages with stable
  references. Retrieved instructions remain quoted historical content, not new
  authority over the current session.
- Decide explicitly how imported provider archives become visible to agent search.
  If the native history tool cannot access them, provide a narrow read/search
  adapter or supported import path rather than silently claiming they are covered.

4C. Memory editor

- Add a memory editor under Tools for the configured Hermes memory provider.
- Discover its real read/update semantics and limits. Do not assume all installations
  use only plain Markdown or expose the same memory implementation.
- Support viewing, editing, adding, and deleting entries through the existing
  supported mechanism. Keep user profile memory distinguishable where applicable.
- Read the latest version before saving and handle concurrent changes explicitly.
  Do not overwrite a whole stale memory file over newer agent-authored changes.
- Explain when a saved change applies to new sessions versus current context.
  Do not claim the active model has already reread a frozen session snapshot.
- Keep project reference material separate from global personal memory unless the
  user deliberately promotes it. An imported chat is not automatically a memory.

4D. Gemini, Claude, and ChatGPT history import

- Support user-provided exports from all three providers, one actual format at a
  time. Inspect representative exports before implementing parsers. Formats and
  included data may vary; never invent their current schemas or promise absent
  attachments/memories are included.
- Preserve provider, original identifiers, timestamps/timezone interpretation,
  title, speaker roles, message order, branch relationships where present, and
  attachment references. Distinguish absent original data from parser failures.
- Import into a searchable archive using supported ingestion or an archive adapter.
  Do not arbitrarily patch upstream database rows to imitate native execution.
- Give imported conversations a source label. Repeated import should deduplicate
  by stable provenance/content identity, without conflating distinct messages that
  happen to have the same text.
- Preview import counts, unsupported records, and any duplicate/conflict handling.
  Retain original exports until the user decides what to do with them.
- Link records across providers through explicit project selection or user action;
  do not pretend unrelated provider conversations form one shared live session.
- Summaries or memory extraction are optional reviewable follow-on actions. Do not
  overwrite live memories or launch expensive whole-archive LLM processing silently.
- Include imported chats in UI search and agent retrieval once the supported path
  is implemented. Preserve source citations when using them as context.

Acceptance

- Star an answer, add it to a project, reopen the app/project, and find the same
  saved item with its source. Add an independent note and an existing attachment.
- Ask a new chat a question requiring a selected project fact; demonstrate the
  selected context/retrieval path, not merely a model's claim to remember it.
- Select context from another conversation and follow its source reference back.
- Keyword search works with embeddings disabled; semantic mode starts off and
  enables only on deliberate selection. Filters change results correctly.
- A real Hermes request searches a past Bellpull conversation and cites/opens the
  matching messages. Verify whether imported history is also covered.
- Edit memory and verify actual persistence and effective timing. Exercise one
  concurrent-edit conflict without losing the newer change.
- Import sample exports from Gemini, Claude, and ChatGPT; rerun import without
  duplicates. Unsupported portions are counted and reported truthfully.

PHASE 5 — COMPLETE NATURAL VOICE CONVERSATION
============================================================

Goal: local conversational voice that feels responsive and works through the
phone's real audio lifecycle. The user selected ALL ten voice menu features.
Whisper is a speech-to-text family; speech synthesis requires a separate TTS model.

5A. Local dictation and local speech output

- Inspect the current read-aloud provider. Existing read-aloud is not proof of
  local synthesis. Preserve the feature while adding a verified local route.
- Select compatible STT/TTS services on Moe or the phone after checking installed
  runtime support, audio formats, latency, memory, and licensing/deployment fit.
  Do not assume an NVIDIA/CUDA-only package accelerates on the V620s.
- Send microphone audio to the chosen private endpoint; display transcription
  state and allow review/correction before sending in dictation mode.
- Offer available voices and speech rate. Handle models loading/unavailable.
- Let the user stop playback immediately. Keep answer text available even when
  audio fails. Never speak tool payloads, emitted thinking, or credentials by default.

5B. Conversation loop and streaming

- Support push-to-talk and continuous conversation with clear listening, processing,
  thinking, speaking, muted, interrupted, and disconnected states.
- Detect speech and end-of-turn pauses. Tune for natural hesitation, not only a
  fixed very short silence timeout. Provide a simple way to hold/control a turn.
- Filter silence/noise appropriately so phantom transcriptions do not launch tasks.
- Stream speech from coherent answer chunks while generation continues. Avoid
  waiting for the full reply and avoid starting TTS on arbitrary partial tokens.
- Preserve one coherent text transcript and align spoken chunks to that transcript.
- Voice should use the same conversation/project/tool context and configured
  permissions. It must not be a disconnected chatbot with a separate memory.
- A low-latency voice preset may prefer thinking off/minimum where supported,
  but keep that choice visible and independent of the typed-chat preference.

5C. Interruption, echo, and correction

- Keep a deliberate interruption path while generating and while speaking.
  Speaking over a reply should promptly stop audible playback and cancel or
  redirect the relevant in-flight work as supported by the session contract.
- Cancel stale buffered audio so it cannot play after the next user turn begins.
- Implement echo handling for phone speakers; do not solve echo by permanently
  disabling the microphone during speech, which would defeat spoken interruption.
- Track acknowledged playback progress. Annotate the transcript/context to indicate
  which portion was played before interruption, without pretending playback proves
  the user consciously heard every word. Retain the full generated text for review.
- Allow transcript corrections before sending and an explicit correction flow
  after sending. Preserve provenance instead of silently rewriting completed tool
  actions based on a later transcription change.
- Clarify the distinction between "stop speaking", "stop this answer", and
  cancelling an already-started external task. Cancelling audio cannot undo a tool.

5D. Android audio integration

- Implement microphone permission, appropriate foreground service/media session,
  audio focus, device routing, and current Android background restrictions.
- Support Bluetooth/headphones, screen lock, app switching, and fold transitions.
- Handle incoming calls, audio-route changes, headset disconnection, interruptions
  from other media, and connection loss without leaving a hot mic unintentionally.
- Show an obvious microphone/voice-session indicator and a reliable stop control.
  Do not add always-listening wake-word capture to this scope by assumption.
- Keep approval/clarification requests reachable during voice sessions. A spoken
  response should use the same approved decision path as the existing UI.

Acceptance and performance evidence

- Dictate, correct, and send a message; speak a reply with local services and no
  unannounced cloud fallback.
- Hold a continuous conversation and switch to push-to-talk without losing context.
- Speech begins before a long answer fully completes and does not read thinking.
- Interrupt during generation and during playback; old audio never resumes later.
- Demonstrate speaker echo handling and headset operation on the actual phone.
- Lock the screen and change audio routes; explain any actual OS limitations.
- Preserve text and usable recovery when STT/TTS/network fails.
- Measure end-of-speech to final transcription, first answer token, and first
  audible response, plus interruption latency. Record warm/cold and representative
  long-context behavior. The reported 50 tok/s is not an end-to-end voice guarantee.

PHASE 6 — REMOTE CODING SESSION CONTROL
============================================================

Goal: steer one or more coding agents from the phone. The initial requirement is
session supervision/control, not building a complete mobile IDE.

6A. Runner integration and session identity

- Investigate supported current programmatic interfaces for Codex CLI and Claude
  Code on the host. Prefer structured session/events/approval APIs where available.
  Use the existing Hermes process/PTY facilities when they are the smallest
  workable route, without pretending PTY text guarantees native steering support.
- Create the smallest runner adapter needed to list/start/attach to/resume sessions,
  send input, read output, inspect status, and stop work through the supported path.
- Distinguish a Hermes session/run ID, a child process handle, and the coding
  runner's own conversation/session ID. Keep ownership and routing explicit.
- Include runner type, workspace, actual model when available, current state,
  last activity, and pending human requests. Keep workspace selection deliberate.
- A CLI subscription/auth configuration belongs to that runner. Do not assume it
  uses the same local Qwen endpoint or credentials as Hermes; report actual routing.
- Prefer direct deterministic control calls for session actions. Do not require
  a Hermes model turn merely to switch tabs, fetch logs, or send an exact steer.

6B. Multiple-session interaction

- Show multiple active coding sessions in Tools/the coding workspace and integrate
  them with the Running/Unread dashboard.
- Provide distinct "Queue" and "Steer" actions where the runner genuinely supports
  them. Clearly label interruption/restart behavior where true steering is absent.
- Queue is a coding-session behavior. Ordinary chat keeps the simpler composer,
  editing, and branching flow selected by the user.
- Show queued requests and allow safe editing/removal before execution.
- Route every input to an explicit session; switching visible sessions must never
  redirect a pending submission to a different runner.
- Keep separate drafts per coding session and handle output while a session is
  not visible. Multiple sessions must not mean multiple writers blindly changing
  the same checkout; use deliberate workspace/worktree choices where necessary.
- Surface real runner approval/clarification requests. Do not bypass runner policy
  or answer privileged prompts through insecure plain-text logging.
- Reuse grouped tool cards when structured events exist. Use honest text/log
  output when they do not; do not manufacture structured progress.
- Reconnect to the same ongoing work and preserve completed receipts/status.
  Do not claim a terminated child survived a server or parent-process crash.

6C. Optional response comparison

- Put response comparison under Tools as requested, after core controls work.
- Let the user select two configured routes and send the same selected context
  intentionally. Label model, reasoning settings, and response source.
- A default comparison should produce answers without duplicating side-effecting
  tool actions. Any tool-capable comparison needs explicit scoped behavior.
- Schedule sequentially if local VRAM/model loading makes concurrency impractical.
  Do not evict a live conversation's model without a visible, deliberate policy.
- Full file editing, extensive Git UI, PR creation, and IDE-grade diff workflows
  are not required for the first coding release. Add only if later selected.

Acceptance

- Start or attach to two coding sessions, preferably exercising both runner types.
- Observe independent status/output/drafts; steer/queue target the intended one.
- A queued request executes once; an unsupported steer is honestly explained.
- Resolve a real runner approval and recover its state after reconnect.
- Lock/reopen Bellpull and locate the same host work without spawning duplicates.
- Record exact runner versions, adapter capabilities, and crash/retention limits.

PHASE 7 — TODAY, ANDROID ASSISTANCE, AND ON-PHONE FALLBACK
============================================================

Goal: add the later personal-assistant capabilities without making core online
chat depend on solving every phone integration or local-inference problem.
Deliver the following slices independently where dependencies allow.

7A. Today, reminders, and follow-up tracking

- Replace the Today "Coming soon" state with due reminders/tasks, unfinished
  follow-ups, pending approvals, and active work. Use existing records directly;
  opening Today must not require an LLM to reconstruct the entire screen.
- Reuse existing Hermes scheduling/task facilities or configured services first.
  Add minimal task metadata only when no usable authority exists.
- Create, complete, reschedule, and cancel reminders through validated operations.
  A simple completion tap must not require a chat turn.
- Track unfinished requests with a clear source link and explicit resolution.
  Avoid inventing promises or inferring every casual sentence as a new commitment.
- Distinguish server reminders needing delivery from alarms scheduled on-device.
  Show where a reminder runs so offline behavior is understandable.
- Use the user's configured timezone (initially America/Los_Angeles), handle DST,
  and ask about a genuinely ambiguous requested time rather than guessing badly.
- Proactive assistance should be configured and attributable to a routine or
  user-selected trigger. Avoid continuous environmental monitoring by default.

7B. Calendar awareness and notification reading

- Add read-only calendar viewing and selected-calendar context first, using the
  existing account/device calendar source and permission model where available.
- Preserve event timezone/all-day semantics and expose event freshness. Calendar
  creation/editing is a later explicit capability, not implied by awareness.
- Support reading selected Android notifications through the supported platform
  service and a deliberate user-granted setting. This is separate from Bellpull
  posting notifications about its own messages.
- Let the user select included apps/categories and whether content is forwarded
  to Moe or read aloud. Avoid indiscriminate forwarding of private notifications.
- Treat notification content as untrusted data, never tool authorization. Preserve
  a manual way to exclude sensitive app content and to stop reading aloud.

7C. Device entry points and actions

- Ship the home-screen bar widget described in NAV07. Reuse app search and new-
  chat drafting, adapting behavior to the actual widget framework's limitations.
- Add a Quick Settings tile for opening Bellpull, starting a new chat, or user-
  initiated voice as permitted. Choose a clear default and expose alternatives
  only if they fit existing settings patterns.
- Add a small set of explicit device actions first: app launching and supported
  alarm/reminder actions. Expand through supported APIs, intents, or narrow tools.
- Declare permissions when the corresponding feature is requested. Keep remote
  phone actions tied to the authorized device/session and current access grants.
- Investigate the platform's default-assistant role and integrate it when feasible.
  Respect lock-screen limits. Becoming an assistant does not grant arbitrary
  access to other apps, device settings, or background microphone capture.
- Do not turn this project into a custom ROM, launcher replacement, broad
  accessibility automation system, or phone root project without a new request.

7D. Bounded CPU-inference feasibility study

- Candidate requested by the user: Gemma E2B on CPU for responsive local fallback.
  Resolve the exact model/release, format, quantization, license, and runtime at
  implementation time. The discussion also referred to Gemma 4 E2B; do not silently
  substitute a different model when that identifier cannot be verified.
- The user's previous phone-GPU attempt was unsuccessful. Establish a CPU baseline
  first. Do not burn open-ended time repeating unsupported GPU experiments.
- Inspect existing attempts/logs before selecting a small number of plausible
  runtime paths. Reuse a minimal native integration, not a new inference framework.
- Measure cold load, prompt processing at several useful context lengths, first
  token, generation rate, resident memory, thermal throttling, and battery impact
  on the actual phone. Benchmark a realistic conversation, not only a tiny prompt.
- Check output quality, schema/tool adherence where needed, cancellation, and
  Android lifecycle. A model that prints tokens is not yet a safe agent fallback.
- Report whether it is useful for chat, local search summaries, or limited actions.
  Limit the fallback's tools to capabilities it can demonstrably handle.
- If infeasible, retain offline drafts/cached reading/search and record the blocker.
  Do not weaken working online features or quietly substitute a cloud provider.

7E. Local/server policy and synchronization

- Working interpretation of the user's "merge the two" request: merge phone-local
  and Moe conversation/knowledge records after reconnection, with user resolution
  of genuine conflicts. Confirm this interpretation before a consequential schema
  migration; it is an interpretation, not a verbatim finalized sync design.
- Show On phone versus Moe and the selected route. Make fallback behavior explicit
  and configurable. A connection outage must not silently send private data to an
  unconfigured external provider.
- Use stable IDs, record revisions, provenance, deletion markers where required,
  and idempotent sync batches. Automatically merge independent additions.
- Preserve diverging conversation branches. Detect concurrent edits to the same
  note/memory/project record and offer a focused conflict decision.
- Keep original versions until resolution. Avoid last-write-wins data loss based
  solely on device clocks or concatenating two live database files.
- Completed tool actions remain completed. Syncing history must not replay sends,
  file mutations, reminders, or other side effects. A queued but unexecuted action
  needs explicit current-state validation before eventual execution.
- Reconcile read/delivery state separately from text and memory. Preserve deleted
  records' intent so old caches do not resurrect deliberately removed content.
- Do not merge arbitrary provider policy/system configuration automatically.
  Keep permission decisions under the appropriate agent/device authority.

Acceptance

- Create/reschedule/complete a reminder and see its status in Today; follow-up
  records lead back to the source conversation and can be resolved.
- Test local timezone/DST handling and actual notification/alarm delivery path.
- View selected calendars and correctly interpret an all-day and timed event.
- Grant/revoke notification-reading access and restrict included apps; Bellpull's
  own notification delivery continues independently.
- Quick tile/widget entry preserves current work and starts the intended action.
- Default-assistant behavior is tested on-device or explicitly marked unverified.
- CPU feasibility has reproducible measurements and a clear go/no-go conclusion.
- If fallback is viable, go offline, create local work, reconnect, merge independent
  records, resolve a concurrent edit, and verify that no tool executes twice.

DATA CONTRACT CHECKLIST — LOGICAL CONCEPTS, NOT PRESCRIBED TABLES
============================================================

Use existing schemas wherever possible. These are the relationships that must be
represented somewhere, not a request to add a table for every line:

- Conversation/session: canonical identity, backend/runner identity, source,
  title, mode, project references, effective model route, active branch.
- Message: stable identity, author, ordered content, branch/source references,
  attachments, optional emitted reasoning, tool references, timestamps.
- Run: identity, submitted request identity, owning session, lifecycle, active
  controls, current status, event/history recovery position.
- Tool event: identity, owning run/turn, ordered timestamps, state, arguments,
  result/error, approvals where genuinely required.
- Draft/outbox: chat identity, editable draft, selected attachments/quote, delivery
  identity, acceptance state. Distinguish editable text from accepted submissions.
- Read position: device/user scope and last actually viewed content; avoid inferring
  read state from a server completion timestamp.
- Saved item: stable identity, source message/attachment, retained excerpt or note,
  version, star state, project memberships, context-inclusion preference.
- Project: stable identity, name, collection membership, selected reference notes/
  files, optional existing workspace binding, no implicit new agent.
- Attachment/artifact: stable identity, MIME/name/size, authenticated access,
  source associations, availability, derived preview/extraction relationships.
- Memory: existing provider's identity/version/edit semantics and scope.
- Coding session: runner identity/version, owning host/workspace, native session ID,
  controls actually supported, pending input/approval, readable status.

Important invariants:

1. One logical submission cannot become two runs merely because a phone retried.
2. Switching the foreground chat cannot retarget already composed/queued input.
3. Display/history replay cannot execute a completed tool.
4. A saved item's source can be resolved or explicitly reported missing.
5. Projects and semantic search do not silently expand the model's context without
   a bounded retrieval/inclusion policy.
6. Missing telemetry, permissions, or backend capabilities are not fake success.
7. Provider imports preserve source identity; sync preserves branches and edits.

- Read the progress record and inspect the current implementation. Avoid redoing
  finished phases after context compaction.
- Identify the smallest end-to-end outcome, touched components, and acceptance
  scenarios. Reuse existing behavior and fixtures where possible.

While implementing:
- Prefer vertical slices that include working UI, actual state changes, and the
  minimum backend wiring. Mocked future features must be labeled accordingly.
- Keep unrelated changes out. Preserve user changes and use an isolated branch/
  worktree when the repository workflow calls for it.
- Use a backup/versioned migration for data changes. Test migration with existing
  conversations and attachments, not only a pristine installation.
- Use supported platform APIs and the exact installed dependency versions.
  Consult current primary documentation when a technical contract is uncertain.
- Do not bypass a failing capability check with fabricated events or silent no-ops.
- Avoid exposing credentials, full private chat archives, or notification contents
  in logs and automated test artifacts.

At each completed slice/phase:
- Build with the repository's established command.
- Run focused behavioral verification for the state transitions changed. Test
  real integration paths when access exists; state limitations when it does not.
- Review the touched UI on cover/unfolded layouts and light/dark themes. For purely
  backend slices, focus on their actual contract and failure behavior.
- Check baseline chat, stop, branching, tool expansion/copy, prompt-history search,
  and context panel for regressions relevant to the touched code.
- Make a local checkpoint commit when the repository workflow permits; do not
  push, merge, publish, or deploy by assumption.
- Update progress with requirement IDs/slices, files changed, behavior delivered,
  validation evidence, remaining risks, and exact next steps.
- Continue to the next ready slice without asking whether to keep doing work that
  is already covered by the user's implementation request.

Suggested progress record fields:

  Phase / slice:
  Status: pending | in progress | implemented, unverified | verified | blocked
  Existing capability reused:
  Changes and important decisions:
  Schema/API changes, if any:
  Build/test/device evidence:
  What remains unknown:
  Blocker and smallest next action:
  Commit/reference:

Do not label an entire phase complete because its UI shell exists. A preview
button that cannot fetch a PDF, a semantic toggle without retrieval, a reasoning
selector ignored by inference, or a notification that only works in the foreground
is unfinished integration, not feature parity.

When blocked, report the specific missing interface/access/asset and continue
independent work. Ask one focused question where a user decision is genuinely
needed. Do not transform every engineering choice into an approval ceremony.
