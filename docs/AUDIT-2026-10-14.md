# Bellpull project audit — 2026-10-14

Bellpull's current Android and plugin regression suites pass, but six additional
defects were reproduced. **Fix workspace preview command execution and the calendar
sharing revocation race before promoting this branch.** Three further defects affect
transcription URL validation, proposal retention and workspace file containment;
one causes a successful calendar edit to be reported as a failure.

The pinned Hermes host images also contain dependency versions with published
security advisories. Those matches need a host upgrade and a reachability review;
they are recorded separately from reproduced Bellpull defects.

This is an audit report and evidence bundle. Product fixes are not part of this
commit. Severity reflects impact in Bellpull's documented single-owner deployment,
including each finding's prerequisites; it is not a calculated CVSS score.

The review covered first-party Android application and transport code, the Bellpull
server plugin, optional legacy host overlays, native speech integration, desktop
launcher, build and CI configuration, dependency inventories, release documentation,
and the 13 open issues. Methods combined source inspection, fresh regression builds,
isolated fault probes, dependency advisory queries and documentation comparison.
Code links below are pinned to the audited revision.

Tests used disposable data, fake inference and network-isolated containers. The
audit did not access the personal Hermes server, run real inference, change the
installed phone app, or inspect personal calendar data. Existing device acceptance
records are identified as historical evidence. Untracked personal files were
excluded from review and publication.

This is a broad engineering audit, not a penetration-test certification or a
line-by-line review of every vendored dependency. The API bearer key is already
root-equivalent on the Hermes host; Bellpull is not a multi-tenant security boundary.

### F01 — Workspace previews execute Git clean filters

**Affected code:** [`coding_workspace.py`, lines 17–43 and 72–84](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/plugins/bellpull/coding_workspace.py#L17),
called by the authenticated [workspace handler](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/plugins/bellpull/coding.py#L389).

The Git subprocess disables hooks, filesystem monitors, external diff and textconv,
but still reads repository-local filter configuration. `git diff ... HEAD --` can
invoke a clean filter while examining a changed worktree file. Disabling textconv
does not disable this separate mechanism. Git documents clean/process filter
execution in its [attributes reference](https://git-scm.com/docs/gitattributes#_filter).

**Reproduction:** create a disposable Git repository with a tracked file and a
matching `.gitattributes` entry. After the initial commit, configure that file's
clean filter to run `touch audit-filter-executed; cat`, modify the file, and call
`inspect_workspace()`. The marker is created even though the caller only asks for
the list of changed files. The published probe creates and deletes its own fixture.

**Impact and prerequisites:** opening the preview can run commands as the Hermes
server user. The workspace must already contain a configured filter; an ordinary
clone containing only `.gitattributes` is insufficient. This is not an
unauthenticated remote exploit. It matters when a coding task or another workspace
writer can configure a filter and the user later opens the advertised read-only
preview. Even legitimate filters can have unintended side effects.

**Repair:** derive changes from object/index metadata and bounded descriptor-based
file reads without invoking worktree conversion filters. Explicitly account for
repository-controlled Git configuration. Ensure timeout cleanup covers descendant
processes. Add marker-based regressions for both `filter.*.clean` and
`filter.*.process`, including preview-list requests.

### F02 — Revocation does not fence older calendar uploads

**Affected code:** [`PlanningWorkspace.savePolicy/syncCalendar`](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/android/app/src/main/java/org/praxisog/hermes/PlanningWorkspace.kt#L95),
[`HermesClient.shareCalendar`](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/android/core-hermes/src/main/kotlin/org/praxisog/hermes/core/HermesClient.kt#L121),
and [`PlanningStore.calendar`](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/plugins/bellpull/planning.py#L112).

Changing the sharing policy cancels the refresh coroutine and starts a new refresh.
The old upload is a synchronous OkHttp call inside `withContext(IO)`; cancelling the
coroutine does not cancel that transport call. The new refresh can successfully
revoke sharing before the old upload reaches the server. Revocation deletes the
calendar row without leaving a generation or tombstone, so the server accepts the
older upload as a new snapshot.

**Reproduction:** the Android probe holds an upload inside an interceptor, turns
sharing off, waits for the revoke response and `revokePending=false`, then releases
the old upload. The observed commit order is `[revoke, upload]` while the saved
policy remains off. A separate server probe submits the same ordering to
`PlanningStore` and confirms that the calendar cache is restored. No real calendar
account or network service is used.

**Impact:** calendar data can remain available to Hermes after Bellpull reports
revocation complete. The same ordering defect can restore a broader calendar
selection or a detailed snapshot after the user selects busy-only sharing. Those
additional policy transitions follow the same code path; the reproduced case is
sharing on → off.

**Repair:** persist a per-device policy generation on both sides. Revocation must
advance that generation and retain a tombstone; reject uploads from older
generations. Cancel/join obsolete transport work as well, but do not depend on
client cancellation alone for server ordering. Test delayed uploads, process
restart, selection narrowing and detailed → busy-only transitions.

### F03 — Transcription HTTP validation drops nonnumeric hostname labels

**Affected code:** [`PrivateTranscription.validateEndpoint`, lines 54–69](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/android/core-hermes/src/main/kotlin/org/praxisog/hermes/core/PrivateTranscription.kt#L54).

The validator builds IPv4 octets using `mapNotNull { it.toIntOrNull() }`. This
discards DNS labels instead of rejecting them. Consequently these results occur:

```text
http://example.invalid/v1/audio/transcriptions                 REJECT
http://100.64.0.1.example.invalid/v1/audio/transcriptions       ACCEPT
http://100.64.0.1/v1/audio/transcriptions                       ACCEPT
```

The second URL is a DNS name, not a Tailscale IPv4 literal. The `.invalid` suffix
is intentional: the probe only validates strings and makes no network request.
The same shape can be registered under a real public domain.

**Impact and prerequisites:** a user must configure such an endpoint. Bellpull
then permits cleartext HTTP for recorded audio and the separately configured
speech-service key despite claiming HTTP is limited to Tailscale or loopback.
The Hermes bearer key is not sent by this client. Default offline speech input
does not trigger this finding.

**Repair:** require exactly four numeric labels before evaluating an IPv4 range;
reuse the stricter endpoint parser where practical. Cover extra alphabetic labels,
extra numeric labels, malformed octets and valid private endpoints in regression
tests. Retain the existing redirect prohibition.

### F04 — Resolved calendar proposals exhaust a lifetime limit

**Affected code:** [`PlanningStore.propose/resolve`, lines 151–174](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/plugins/bellpull/planning.py#L151).

Admission rejects a proposal when `COUNT(*) FROM proposals >= 100`. Resolving a
proposal only changes its JSON state; completed and rejected rows remain in that
count. There is no normal terminal-proposal retention policy.

**Reproduction:** create and reject 100 proposals, then create one more. With zero
pending proposals, the server returns HTTP 409 and tells the user to resolve old
proposals. Repeating resolution cannot recover the feature. Revoking calendar
sharing deletes that device's proposals, but is a disruptive workaround rather
than the requested resolution action. The limit is shared across the profile's
devices, so one device's history can block another.

**Repair:** separately bound pending work and retained terminal history. Keep
bounded idempotency receipts when pruning so an old retry cannot recreate an
already applied proposal. Test over 100 sequential create/resolve operations,
multiple devices, retries and retention-boundary behavior.

### F05 — Workspace file containment excludes symlinks but permits hard links

**Affected code:** [`owned_bytes`, lines 46–69](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/plugins/bellpull/coding_workspace.py#L46).

Descriptor-relative traversal and `O_NOFOLLOW` block symlinks, but the final
regular-file check does not reject `st_nlink > 1`. An in-workspace directory entry
can therefore refer to the same inode as a file outside the workspace.

**Reproduction:** create `outside.txt` beside a disposable repository, hard-link
it into the repository as `linked.txt`, list workspace changes and request that
file's diff. The preview contains `AUDIT_OUTSIDE_WORKSPACE`; the inode has two
links. The artifact collector already applies a stricter hard-link rule, so the
two file-reading boundaries have inconsistent policies.

**Impact and prerequisites:** a local writer must be able to create the hard link
on the same filesystem, and the Hermes process must be able to read the file.
This does not bypass OS file permissions or make arbitrary remote path selection
possible. It nevertheless exposes bytes outside the intended workspace boundary
through a preview presented as contained. Medium severity reflects that privacy
boundary, with the local-writer prerequisite limiting exploitability.

**Repair:** reject multiply linked files before reading, or use a deliberately
trusted immutable snapshot with equivalent containment guarantees. Add hard-link
regressions alongside existing symlink tests. Document any compatibility impact
for users who intentionally share worktree files through hard links.

### F06 — Calendar title normalization happens after the success comparison input

**Affected code:** [`PhoneCalendar.change/values`, lines 92–119](https://github.com/PraxisOG/Bellpull/blob/4fc426f22379babed067120b54705bcb23fb6d47/android/app/src/main/java/org/praxisog/hermes/PhoneCalendar.kt#L92).

The write stores `draft.title.trim()`, then verifies the result against the original
untrimmed `draft.title`. Editing a title to ` After ` commits `After` successfully
but throws “Calendar result differs. Refresh before another edit.” Creation already
uses a trimmed comparison, making editing inconsistent.

**Reproduction:** the existing CalendarContract fixture confirms the persisted
title is `After` while `change()` throws. The probe exercises the actual adapter,
not a reimplementation of its comparison.

**Impact:** users receive a failure for a completed write and can be left with an
uncertain local operation receipt. Refresh is needed before another edit; a
retry can then conflict with the changed event fingerprint.

**Repair:** normalize the draft once and use it for both mutation and verification.
Add a regression that verifies the user-visible success and receipt state after
an edit with leading/trailing whitespace.

## Dependency and supply-chain review

### D01 — Pinned host images contain versions with published advisories

**Priority: medium, pending deployment-specific reachability.** The scan enumerated
139 Python distributions in the legacy fixture and 142 in the modern stock image,
then queried 147 distinct package/version pairs. Nine coordinates across eight
package names matched 33 unique GHSA records. CVE/PYSEC aliases were not counted
as additional vulnerabilities. Both images include all eight names; Tornado has
a different version in each.

| Package | Installed version(s) | Upstream remediation recorded by the queried advisories |
|---|---|---|
| PyJWT | 2.13.0 | Most fixes in 2.14.0; two in 2.15.0; one options-dictionary advisory has no fixed version in its record |
| anyio | 4.12.1 | 4.14.2 |
| httpcore2 | 2.7.0 | 2.10.0 |
| httpx2 | 2.7.0 | Fixes through 2.12.0 |
| multidict | 6.7.1 | 6.9.1 |
| oauthlib | 3.3.1 | 4.0.0 |
| tornado | 6.5.7 legacy; 6.5.8 modern | Fixes through 6.5.9 |
| urllib3 | 2.7.0 | 2.8.0 |

These are advisory-record versions, not a tested upgrade set. Full identifiers,
aliases, image membership, upstream severities, fixed versions and source URLs
are in [dependency-findings.json](audits/2026-10-14/dependency-findings.json).
Installed inventories are in [host-python-dependencies.json](audits/2026-10-14/host-python-dependencies.json).

Two examples illustrate why package matches need contextual review. AnyIO's
certificate-validation advisory requires an internationalized hostname and a
connection redirected to an attacker; that condition was not established for
Bellpull. urllib3's chunk-header buffering advisory concerns streaming responses
from a malicious HTTP endpoint. Both affected versions are present, but no exploit
was attempted against a configured provider. See the upstream
[AnyIO advisory](https://github.com/agronholm/anyio/security/advisories/GHSA-82r6-8w77-94w6)
and [urllib3 advisory](https://github.com/urllib3/urllib3/security/advisories/GHSA-vxq7-64xx-v4gw).

Bellpull's own API authentication uses the host's bearer-key check, not a PyJWT
verification flow. Finding PyJWT in the image therefore does not establish a
Bellpull authentication bypass. The HTTPX2 WebSocket/SOCKS, Tornado handlers and
OAuth-specific advisory paths likewise need feature-level reachability analysis.

**Action:** select an updated supported Hermes image, inspect its resolved
dependencies, rerun compatibility and migration tests, then update the digest
pins. Add recurring advisory scanning for both supported host variants. Preserve
the reviewed overlay hash gates; forcing arbitrary dependency versions into the
legacy host can invalidate compatibility assumptions.

## Recommended repair order

1. Fix **F01 and F02** with deterministic regression tests. They undermine explicit
   read-only and privacy guarantees.
2. Fix **F03–F06** and run the focused transport, workspace and planning suites.
   Keep revocation and operation-identity behavior compatible during migration.
3. Refresh and requalify the host images for **D01**; add automated dependency
   scanning and resolve or document each advisory's affected code path.
4. Add resource ceilings and capacity tests for **H01/H02**, then complete the
   wrapper/model-integrity and documentation work in **H03–H05**.
5. Complete the outstanding physical audio-route and provider acceptance before
   calling the experimental reliability work fully accepted. Publish a clearly
   paired app/plugin release when that release is requested and ready.

Keep the same account, profile and server-ownership boundaries during remediation.
Passing today's suites is useful evidence, but the reproduced failures above show
why the new adversarial cases must become permanent fixed-behavior tests.
